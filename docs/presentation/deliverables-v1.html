B
AI approach — and where we deliberately didn't use it

One model, in the one place rules structurally cannot go.

We use Claude in exactly one spot: reading a vendor's free-text reply into a structured order event. Everything else is deterministic on purpose.

The rules-based baseline is keyword/regex matching — /yes|confirm/ → accept, datetime regexes for ETAs. It fails on a whole category of input, not just hard cases: "we can grab the equipment Friday" carries no keyword for pickup, and the parser must also resolve which order an unreferenced text is about (we pass the vendor's open orders as context) and turn "Thursday morning" into a timestamp. Rules can't represent either without becoming a fragile mini-NLU engine.

Where the model earns its place
  • Open-vocabulary vendor prose — every new vendor is a new dialect; a model handles the long tail natively.
  • Order inference — resolving which open order an unreferenced reply means.
  • Relative-time resolution — "Thursday by 10" → a real deadline the risk engine can use.
Where we refused to spend a model
  • Risk scoring — a rules engine, so every score is a sentence a case manager can argue with.
  • Reply-code addressing — a bare "7" routes to the right order by arithmetic, no inference.
  • Caregiver rating — a digit is a digit; deterministic regex, no model.
  • The magic-link tap — confidence 1.0, no model in the path of a state change.

Safety: a human gate between the model and any state change

Structured output only

The parse is schema-constrained (JSON schema enforced at the API level). The model classifies and extracts; it cannot invent fields, statuses, or patient details.

Confidence gate → review queue

Auto-applies only at ≥ 0.8 with a resolved order. Anything less lands in a visible review queue where a person confirms or dismisses. With no API key, the pipeline degrades to the queue rather than guessing.

The state machine is the backstop

Even an auto-applied parse can only fire a valid transition. A hallucinated "delivered" on an order still in ordered is rejected with a 409 and falls to review.

The rules, backtested honestly — on synthetic data synthetic

npm run backtest replays every seeded order tick by tick exactly as the watchdog would have seen it — state rebuilt from the event ledger, a flag only counts if it fired before the deadline. Against the shipped threshold of 70, the risk engine flagged 78% of late deliveries a median 8.7 hours early, with false alarms on 27% of on-time orders (n=203). We keep the false-alarm rate in the open: most of those flags were reasonable when they fired. This shows the approach — explainable rules over per-vendor × equipment × weekday history — not field performance, because there is no public DME delivery-timing dataset.

Silence is a reading, from hour one

An unacknowledged order looks exactly like one going fine — until it doesn't. A 30-second watchdog turns non-response into a timestamped event with an owner. The software does the chasing; the vendor is never punished for being busy.

The household is the only witness — so ask it

A condition survey isn't new; who owns the answers is. Today that data lives in the file of the supplier being graded. We invert the direction: the hospice asks, holds the record, and it informs the next referral. The CEO named this at the briefing.

📞

The measure is phone calls that never happened. The saved discharge looks, to the daughter, like nothing happening. The bed is gone by evening without anyone in the house making a call. If we build this right, the family never knows the system exists.

D
Integration approach sketch

DME rides the pipe medications already ride.

We don't design a new EMR integration. A DME order becomes a sibling of the medication events already flowing through BetterRX's eRx — same envelope, same patient join key.

Per FAQ §4, eRx already receives newOrUpdatePatient and newMedications today. So newDmeOrder copies that envelope verbatim: medications[] becomes dmeOrders[], and only NDC → HCPCS changes inside the product block. The two fields with no drug analogue are urgency and targetWindow — because a pill has no discharge deadline and a hospital bed does.

// newDmeOrder — sibling of newMedications
{
  "meta": { "eventType": "newDmeOrder" },
  "patient": {
    "identifiers": [{ "id": "..." }],  // same join key
    "dmeOrders": [{
      "externalId": "9c1f4a02-…",
      "product": {
        "codeType": "HCPCS",   // was NDC
        "code": "E0260",
        "name": "HOSPITAL BED SEMI-ELECTRIC…"
      },
      "urgency": "urgent",        // new: DME only
      "targetWindow": {          // new: has a deadline
        "basis": "dischargeHome"
      }
    }]
  }
}

The reverse direction — dmeOrderStatus — is the new capability eRx doesn't receive today. Its evidence block carries deliveryVerified booleans derived from a POD row, never from a vendor's word, so a consumer can always tell a claim from a proof.

Two paths in — the sponsor's own failure case decides the order

Primary — the nurse in the home built

One tap at the bedside: POST /api/patients/:id/status. The signal comes from the human standing where the truth just happened — no propagation to wait on.

Fallback — ADT via eRx built (sim)

The newOrUpdatePatient event maps to the same function, setPatientStatus(). The ledger records which path fired first; the second is a safe no-op.

This is a precedent, not a hypothesis: Axxess × BetterRX already syncs demographics, status and medications today; HCHB Business Connect is the partner-layer model; MatrixCare × Brightree is bi-directional DME ordering built into the chart — the rung-4 ceiling we design toward without requiring it.

The one honest gap — the identity join

Everything operational already fits the schema. The field it can't hold yet is the external patient.identifiers[].id from the eRx envelope — today patients.id is a local integer. Wiring to the real bus adds that external key as the join. A seam to connect, not a schema to rebuild.
