How it works, in detail.

The same two flows shown above — now with the actual events and endpoints that carry them.

▶ The integration sequence, step by step expand for the full diagram

A UML sequence of the two demo flows. Solid = runs in the demo today; dashed = the production path (the real eRx bus, sketched). Every message maps to a real endpoint or event: the nurse trigger is POST /api/patients/:id/status, the EMR fallback is POST /api/emr/patient-status, verified proof is a POD row, and the sibling events on the BetterRX bus are newDmeOrder / dmeOrderStatus alongside the existing newMedications.

Every order mutation is auditable

State changes run through one applyEvent() path and append to a permanent order-event ledger — nothing is silently overwritten.

A claim is never shown as proof

"Delivered" from a vendor text and "delivered" with a driver photo look different on the board. Verification comes from a POD row, never a vendor's word.

AI only acts when it's sure

Free-text replies are parsed by Claude; anything under 0.8 confidence goes to a human review queue instead of moving the order.
